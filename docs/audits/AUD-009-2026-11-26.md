## SPC and Reed–Solomon integration

MHFE uses the same locked SPC 0.2.0 and RSC 0.2.0 in the root, fuzz and Wasm workspaces. System buffer ownership, isolation, writer and stack cleanup are SPC responsibilities. The former local OS backend and local RS encoder/decoder remain absent. The user-facing program chooses and enforces its isolation policy before reading secrets or starting Rayon; optional default-off flags are not claimed as enabled.

RSC protect uses the same SPC. The MHFE adapter supplies the pinned suite, shortening, roots, public parity dimensions, field range and scratch space under the pinned spec. Correction also checks the BIP39 checksum. The three expect calls remain protected by admitted shape constraints. Published vectors and cross-target profile tests exercise the integration.

The Argon2 WorkArea is reused and still needs its between-call wipe in addition to SPC Drop. Its single native raw cast remains checked for size and alignment. The per-thread native and nested RSC clearing work runs from differing stack positions. It is insufficient to remove one cleanup scope merely because it delegates to the same SPC code.

### AUD-009-ARC001 — Native tests assume every SPC secret allocation is locked

- Scope. src/feistel.rs:320 · src/feistel.rs:325 · src/packing.rs:145 · src/password.rs:269 · src/phrase.rs:268 · SECURITY.md:100-107
- Contract. A best-effort Secret can report unavailable locking. Tests verify secret ownership and properties under explicitly controlled prerequisites.
- Evidence. On exact bd41e4d bytes the native release suite stopped at feistel.rs:320 after is_locked returned false for a newly created Workspace. Other 77 libtest cases passed. Five locations assert locked solely from the target family.
- Impact. The release suite can reject a valid SPC fallback. The denial cause on the first run was not instrumented. This outcome does not establish an implementation error in the lock backend.
- Fix. Keep controlled SPC lock tests. In operation-level tests, check page ownership and any actually required policy or condition the assertion on a verified capability. Avoid replacing the native check with a target-constant expectation.
- Verification. Run the complete Linux release suite and a dedicated controlled lock-policy test. Keep first-failure, normal retry and serial receipts distinct.

### AUD-009-DOC002 — WASM memory documentation overstates physical residue and overflow behavior

- Scope. SECURITY.md:26-28 · SECURITY.md:39-41 · reed-solomon-core 0.2.0:src/field/lanes.rs:67-72 · secret-protection-core 0.2.0:src/stack.rs:134-139
- Contract. Describe the unzeroized source-level value, actual engine/stack behavior and audited runtime evidence separately.
- Evidence. The text says the extra RSC value lies on the stack and stays there on Wasm. Source establishes an extra Copy value without explicit zeroization. Rustc default stack-first overflow traps, while layouts placing data before the stack can overwrite it.
- Impact. The documentation assigns a physical location and persistence beyond the retained evidence and oversimplifies target behavior.
- Fix. State the copy and missing explicit wipe. Explain the default stack-first trap and alternate layout risk. Scope direct erasure evidence to observed artifacts.
- Verification. Review the text against the locked backend and distinguish source observation from optimized runtime memory evidence.

- For RSC 0.2.0, source establishes an extra value with no explicit wipe. Neither x86 native stack clearing nor the portable zeroization tests establish retained physical copies on every optimized runtime.
- The locked native WorkArea was previously blocked in Miri by the SPC mapping protection mode. Its production cast and allocator path match the tested snapshot. Pure Miri evidence is limited to selected calls.
- Android on both targets and iOS device linked in CI. iOS simulator was only linted when exact local evidence is present. None of the mobile paths ran.
- The short final-round fuzz campaign used 60 seconds for each of six targets. Full-duration baseline runs with 12232802 cases belong only to 06d7d00.
