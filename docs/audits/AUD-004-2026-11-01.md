## Review evidence

### Scope and methodology

The review covered every one of the 217 regular files tracked by the core repository, plus its specification gitlink: source and tests, OS-specific code, public API, instructions, build inputs, tooling, workflows, licenses, vendored data, image, current documents and both historical audit/harness trees. All 54 declared public functions, 22 exported top-level items, constants, public fields, variants and associated trait/lifecycle behavior were included. The JSON contains the complete path/digest/depth inventory and 25 operation-review groups.

The recursive inventory contains 405 regular files: 217 root files and 188 files of the pinned specification. Of the specification files, 37 have targeted normative, vector-consumer or integrity review; 151 unrelated research, historical-audit, PDF and maintenance files are recorded at dependency identity/provenance depth. This is a full core audit with an explicit dependency scope, not a claim to have re-audited the entire specification project. Published vector consumers and the normative requirements relevant to every core operation were reviewed. Formal cryptographic arguments were not reproved.

Three reviewers first owned separate native, protocol/API and tooling scopes, then reviewed the historical harnesses in separate scopes. A fourth reviewer independently challenged findings, investigated coverage gaps and checked the coordinator's new harness. The coordinator compared documentation claims with source/specification and ran the shared checks. The final ledger has no unreviewed root file. Unconfirmed candidates were not promoted merely to increase the finding count.

Threats considered include hostile or mistaken typed/file/host inputs, wrong passwords and settings, ambiguous recovery, damaged repair records, OS refusals, compiler/profile effects on practical erasure and build/verification failures. The host engine, host RNG implementation and runtime remain trusted under CORE-54; the host must manage its own strings, memory availability, display policy and process lifetime. A surviving eight-bit check mutant was investigated as a test-power observation, not called a current cryptographic bug.

The main verification environment was Linux x86-64 with Rust 1.99.1 and the workspace Cargo/Rustup homes. Heavy work ran sequentially through the shared lock and memory guard. The fast gate had a 2 GiB cgroup cap; audit/cross builds had 1.5 GiB caps, bounded probes 512 MiB, and RustSec 768 MiB, with swap disabled in those scopes. Static helpers were assigned 128 MiB budgets. These are limits and assigned budgets, not measured peaks. No cryptographic production parameter was lowered and no full-cost corpus was replayed locally.

### Findings

#### AUD-004-API001 — Low — Expected cancellation is returned through the error channel

- **Category:** API.
- **Severity:** low.
- **Status:** fixed.
- **Release blocking:** false.
- **Affected files and builds:** `src/error.rs:80`, `src/cipher.rs:90`, `src/feistel.rs:99`, `src/feistel.rs:116`, `src/wallet_check.rs:127`.
- **Reproduction:** Return ControlFlow::Break from a round, unchecked-container or draw callback. The existing callback-cancellation tests exercise the production path.
- **Expected behavior:** CORE-22 requires a person's cancellation to be a returned outcome rather than an error.
- **Observed behavior:** The callbacks use ControlFlow, but each public operation translates Break to Err(Error::Cancelled). Fresh callback tests pass because they expect that error.
- **Impact:** A consistent, documented API disagrees with the current error/outcome policy. This is not incorrect encryption, lost cleanup or an undocumented runtime regression. Bounded standards, documentation or verification-tool defect; no current medium-or-higher runtime impact demonstrated.
- **Evidence:** Current source and error rustdoc; fast.log: cipher::tests::either_callback_cancels_the_operation and feistel callback test; Independent protocol and completeness challenge.
- **Recommended fix:** Choose an explicit completion/cancellation outcome for the affected public operations and update callers, docs and bindings together. Treat this as an API change; coordinate with mhfe and wallet-tools before implementation.
- **Required verification:** Exercise cancellation at each callback, before each round and during draw; require no result publication on cancellation and successful engine reuse. Compile affected native/browser consumers.

#### AUD-004-API002 — Low — The draw contract does not require a finite host trial budget

- **Category:** API.
- **Severity:** low.
- **Status:** fixed.
- **Release blocking:** false.

### Assessment and limitations

The evidence supports matching protocol outputs on the cases checked, correct current 16-bit seed checking, working four-thread RustCrypto composition, practical Linux erasure on the measured profiles, source/registry consistency and target-specific OS selection. It does not establish full CORE compliance or prove absence of vulnerabilities.

- No proof that every defect was found or independent cryptographic certification.
- Fresh runtime Linux x86-64 only. Cross compilation does not establish Windows/macOS/WASM-host runtime safety. No mobile device/other kernel/page-size execution.
- Full-cost corpora were not rerun; existing RustCrypto CI evidence predates current fixes and is reused only for inspected unchanged cryptographic behavior.
- No complete release-artifact acceptance, archive reproducibility, signature/attestation verification, publication or application/browser integration run.
- No fresh fuzzing/mutation campaign, Miri, ThreadSanitizer or formal timing/aliasing proof.
- Upstream dependency internals audited only at traced call seams; matching registry bytes is provenance, not a complete upstream audit.
- 151 unrelated files of the pinned specification have only identity/provenance coverage, individually identified.
- Host/runtime compromise, privileged reads, abrupt death, arbitrary registers, all future compiler layouts and OS dumps are outside demonstrated erasure guarantees.
- Schema helper handles current keywords and literal duplicate JSON keys; escaped semantic duplicate spellings are outside its contract.
- No measured peak memory; limits are stated caps. Selected command environments retained; bootstrap receipts note missing inherited environment fields.

Application displays/warnings, doubled-password entry, mobile memory admission, runtime browser Argon2 and wallet-tools integration belong to their respective hosts and were not re-audited as applications here. The crate's experimental status and warning against real funds remain material.
