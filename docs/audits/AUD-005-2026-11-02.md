### Findings

#### AUD-005-SEC001 — Medium — Windows can leave Argon2 blocks outside error-report exclusion

- **Category:** SEC.
- **Severity:** medium.
- **Status:** fixed.
- **Release blocking:** false.
- **Affected files and builds:** Windows; `src/os/windows.rs:58-59`, `src/os/windows.rs:81-105`, `src/os/windows.rs:138-153`, `src/engine/native.rs:56-75`, `SECURITY.md:42-48`.
- **Reproduction:** `WerRegisterExcludedMemoryBlock` takes a 32-bit size and Windows limits a process to 512 registrations (`WER_MAX_REGISTERED_ENTRIES`). The implementation stops at the first refusal but still returns the engine. Level 20 needs 513 registrations and level 21 needs 769. Separately, 512 simultaneously live `Secret` allocations consume the process quota before a small work area is created. `aud005 source-findings` evaluates these exact paths without allocating TiB or producing a crash dump.
- **Expected behavior:** `SECURITY.md` says the whole Argon2 work area is left out of Windows error reports, and secret-derived blocks must not silently lose that protection. A host needs either complete exclusion or a refusal/explicit security decision before password material enters the engine.
- **Observed behavior:** Level 20 leaves 512 bytes uncovered; level 21 leaves 1,099,511,628,288 bytes (1 TiB + 512 bytes) uncovered even with no other registrations. After 512 other live registrations, a 65,536-byte work area has no covered block. `Pages::is_out_of_dumps` detects incomplete coverage internally, but `NativeArgon2::new` does not require it and exposes only `is_locked`.
- **Impact:** A Windows crash report produced while Argon2 runs can include unregistered secret-derived blocks. Access to those blocks makes password candidates cheaper to test, as `SECURITY.md` itself warns. Prerequisites are Windows, quota exhaustion or a high memory level, and a crash/report during the operation. No disclosure of the original phrase or password, no actual dump and no cross-platform impact was demonstrated. These limits and the required crash make the finding Medium rather than High and keep it non-blocking.
- **Evidence:** `finding-probes.json` (local), SHA-256 `43ad95158d88da0de88279cdb8e24c39bfe437f72d9cf87ec49b8a26806bc148`; source locations above; [Microsoft's registration contract](https://learn.microsoft.com/en-us/windows/win32/api/werapi/nf-werapi-werregisterexcludedmemoryblock), which names refusal when `WER_MAX_REGISTERED_ENTRIES` is exceeded. Windows runtime was not executed.
- **Recommended fix:** Before starting worker threads or accepting secret input, require complete WER exclusion or refuse the operation with a documented error. If partial protection is intentionally supported, expose an explicit status and narrow the documented guarantee instead. Account for all live registrations, not only the work area's own size.
- **Required verification:** On Windows, hold 512 live `Secret` values and construct a small engine; check the chosen refusal/status path before any Argon2 call. Cover the 513/769 registration arithmetic for levels 20/21 without allocating their full size. Confirm dump exclusion, unregister/drop balance, early thread-construction failure and no secret-dependent fallback.

#### AUD-005-DOC001 — Medium — Cancellation guidance can release an unchecked container and repair card

- **Category:** DOC.
- **Severity:** medium.
- **Status:** fixed.
- **Release blocking:** false.
- **Affected files and builds:** all hosts following the API guidance; `src/repair.rs:18-22`, `SECURITY.md:58-60`, `src/cipher.rs:85-114`; the stale module summary at `src/error.rs:1-2` is part of the same cancellation-documentation migration.
- **Reproduction:** Continue from `on_unchecked`, save its container/card provisionally, and return `Break` at round 13. The production call returns `Ok(ControlFlow::Break(()))` before the reverse comparison. The documents instead permit release once `encrypt` returns `Ok`. `aud005 source-findings` executes this exact callback sequence with a public synthetic engine and records callbacks 1 through 13 and no completed reverse comparison.
- **Expected behavior:** NEW-5/NEW-6 require a cancelled container to remain unverified and forbid passing it to another program before the check passes. RPR-1 permits a repair card only after the final container's creation check passes. Publication must require `Ok(ControlFlow::Continue(container))`, not any `Ok`.
- **Observed behavior:** `Ok(Break)` satisfies the documented condition while verification is incomplete. The error-module header also still names cancellation although `Error::Cancelled` no longer exists and cancellation is now a returned outcome.
- **Impact:** A host can publish an unchecked container and repair card as finished backups instead of reporting cancellation. No incorrect Feistel transformation or corrupt container was demonstrated; the defect is the missed documentation migration after AUD-004-API001. Medium reflects the broken mandatory creation-check contract without claiming direct secret compromise.
- **Evidence:** `finding-probes.json` (local), SHA-256 above; specification NEW-5/NEW-6 at `tests/spec/README.md:442-447` and RPR-1 at `tests/spec/README.md:874-876`; related AUD-004-API001.
- **Recommended fix:** Change both publication conditions to `Ok(ControlFlow::Continue(_))`, explicitly state that `Break` leaves the container and card unverified, and remove cancellation from the error-module summary. Coordinate host documentation so no consumer treats `Ok` alone as verification.
- **Required verification:** Add a production-path regression/doctest for cancellation at `on_unchecked` and the first reverse-check round. Require no final container/card publication on `Break`, successful publication only after `Continue`, and correct engine reuse. Check `mhfe` and browser consumers against the clarified contract.

#### AUD-005-API001 — Low — NFKD byte counting overflows before password-length refusal on 32-bit targets

- **Category:** API.
- **Severity:** low.
- **Status:** fixed.
- **Release blocking:** false.
- **Affected files and builds:** 32-bit WebAssembly hosts; `src/nfkd.rs:24-29`, `src/nfkd.rs:38-70`, `src/password.rs:49-69`; shared passphrase/draw callers of the same helper.
- **Reproduction:** U+FDFA expands to 33 UTF-8 bytes. Repeating it 130,150,525 times gives a 390,451,575-byte input and 4,294,967,325 decomposed bytes (`2^32 + 29`). On a 32-bit target the unchecked `usize` accumulation wraps to 29, enters the success branch and writes the decomposition into a 29-byte buffer. With overflow checks enabled the counting addition panics earlier. The preceding repetition count still fits `u32` and reaches `PasswordTooLong`.
- **Expected behavior:** PW-5 and `Password::new` require every normalized password over 1,024 bytes to be refused before writing, never truncated, and public input should return an error rather than panic (CORE-48, RUST-05).
- **Observed behavior:** Source arithmetic proves a reachable overflow and subsequent bounds panic on 32-bit release builds. The audit did not execute a 32-bit runtime; `finding-probes.json` records `runtimeExecuted: false`.
- **Impact:** Input-triggered denial of service. Rust bounds checks prevent memory corruption, and no silently truncated password or seed is returned. The approximately 372 MiB input requirement and absence of secret compromise bound the severity to Low.
- **Evidence:** `finding-probes.json` (local), SHA-256 above; `src/password.rs:239-245` establishes the 33-byte expansion; specification PW-5 at `tests/spec/README.md:351-354`.
- **Recommended fix:** Use checked or saturating accumulation and stop with the over-limit result as soon as the count exceeds `Password::MAX_BYTES`, without changing NFKD bytes for admitted passwords. Keep the early-stop contract suitable for the shared BIP39 passphrase path, whose limits may differ.
- **Required verification:** Execute the exact boundary and preceding control on 32-bit WebAssembly in release and checked builds; require non-panicking refusal before allocation/writing. Recheck 0, 1, 1,024 and 1,025 normalized bytes and the ordinary Unicode cases without a complete corpus replay.

#### AUD-005-DOC002 — Low — README omits the WebAssembly exception to its 64-bit requirement

- **Category:** DOC.
- **Severity:** low.
- **Status:** fixed.
- **Release blocking:** false.
- **Affected files and builds:** WebAssembly users; `README.md:62-63`, `src/lib.rs:15-18`, `src/engine/native.rs:12-16`, `.github/workflows/ci.yml:147-180`.
- **Reproduction:** Read the unconditional requirement “Rust 1.99 or later and a 64-bit target” beside the next sentence's browser host engine and the explicit 32-bit WebAssembly support in rustdoc and CI.
- **Expected behavior:** DOC-06/DOC-07 require platform guidance to distinguish the native engine's 64-bit restriction from supported 32-bit WebAssembly with a host engine.
- **Observed behavior:** The README can lead a WebAssembly integrator to conclude that a supported target is unsupported.

### Assessment and limitations

The evidence supports the five concrete findings above, successful Linux fast/security tests, a working cancellation outcome at the API level, matching fast protocol cases and a clean RustSec result for the resolved graph. It does not establish absence of other defects or suitability for real funds.

- Fresh runtime was Linux x86-64 only. Windows, macOS, Android, iOS and WASI runtime behavior was not exercised; cross-target source and CI definitions are not runtime proof.
- The 32-bit overflow and Windows WER cases were source/arithmetic-confirmed but not runtime-executed. No Windows crash dump was produced.
- Complete vector corpora and full-cost Argon2 were not replayed. The ordinary fast suite passed; older full-cost evidence was not relabelled as current execution.
- No complete release-artifact acceptance, package reproducibility, signature/attestation verification, publication or application/browser integration run was performed.
- No new fuzzing, mutation campaign, Miri, ThreadSanitizer, statistical timing test, full LLVM/assembly erasure analysis or formal cryptographic proof was performed.
- Upstream internals were reviewed only at traced call seams. RustSec and lockfile/provenance checks are not complete audits of every dependency.
- Host-managed strings, memory admission, display policy, doubled password entry and application warnings belong to host projects and were not re-audited here.
- Memory budgets were assigned limits, not measured peaks. Local evidence retains actual environments; published records anonymize machine paths.
