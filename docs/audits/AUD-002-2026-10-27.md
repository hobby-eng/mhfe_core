## Review evidence

### Scope and methodology

The audit covers the whole repository at the reviewed commit: the library (`src/`, `build.rs`, the C wrapper `argon2_wrap.c`), its tests and fixtures, the vendored trees, the scripts and gates, the three workflows and the documents. The crate is a library: it has no browser, user interface, provider, transaction or HD-derivation surface, and the checks for those are recorded as not applicable with a reason. The procedure is the workspace's: `FULL_AUDIT_GUIDE.md` (32 CHECK tasks), `AUDIT_STANDARD.md`, `AUDIT_TEMPLATE.md`, the report schema and the audits instructions; their SHA-256 are below.

A compact team divided the checks: security (CHECK-SEC-001 to 005 and 007), protocol (CHECK-FUN-001 to 007 and CHECK-API-004), api (CHECK-API-001 to 003 and CHECK-ARC-001 to 003), build (CHECK-BLD-001 to 005 and CHECK-DOC-002) and docs (CHECK-DOC-001, CHECK-DOC-003, CHECK-SEC-006 and CHECK-UI-001 to 003). Each reviewer read the code and documents of its scope, ran the repository's own checks and wrote harnesses of its own; every harness exits non-zero when its check fails. Each reported finding was then challenged by a separate agent with a harness of its own. Nine reports were confirmed, three of them as one defect (AUD-002-SEC001), and two were withdrawn. A remediation agent fixed the nine, and two verification rounds checked each fix against its finding.

Rules of execution: every Cargo, Node.js and pnpm command ran through a memory guard; heavy checks ran one at a time; no full-size Argon2id or `--ignored` test ran locally; cross checks of Rust code used a stand-in C compiler; GitHub was read only, and no workflow was dispatched; public fixtures only. Under CORE-54, the audit reports what a person, a file, the network or the operating system can cause; a failure that needs a trusted part of the program to fail is out of scope. Owner rule: an addition that nothing needs is an ARC finding, and a fix is the smallest change.

Inputs and references: the specification and its vectors (`mhfe_spec` `6f7537e`); mhfe at `67e0b4c`, which the crate was cut from (read only); the cutting plan and its owner decisions; the earlier reviews of this cut (stage 1, stage 2 and M6), used as a regression checklist, where no earlier item regressed. Decisions the coordinator had already taken were not reported as findings: seccomp allows `ftruncate`; macOS reports `PT_DENY_ATTACH`'s answer; the ioctl allowlist is the nine terminal requests; Landlock's device-ioctl right applies to terminals opened after `enter()`; iOS needs `IPHONEOS_DEPLOYMENT_TARGET` 13 or later; the Windows default access list makes later objects unopenable by name; the isolation test drops `SeDebugPrivilege` before checking; the core names the specification by version only; the fixtures hold only the specification's JSON and SHA256SUMS. The owner's decision 8 below later replaced the last two for the published release: the tests read the specification's vectors through a submodule pinned to a commit of the specification.

After the first version of this record the work went on the same day: the owner decided the pending questions; a second remediation made the complete NFKD fix, reverted the move to 0.2.0 and replaced the Node.js tooling with Rust; two reviews of the release changes followed (CORE-53); the harnesses were rewritten in Rust and rerun at `dec9c81` and at a first release commit, where CI also ran. The owner then changed the licence, the badges, the workflows and the source of the test vectors, each change reviewed in turn; the release commit was made again, published as mhfe-core 0.1.0, and replayed at full cost on its tag; and the harnesses whose inputs it changed ran again there. This update records that. Each finding's reproduction, observation and impact still describe the reviewed commit; its first remediation and first verification are kept as recorded, and what happened since follows them.

#### AUD-002-SEC001 — Low — An unbounded BIP39 passphrase makes Seed::derive and wallet_check::draw take time quadratic in a run of combining marks

- **Category:** SEC.
- **Severity:** low.
- **Status:** verified at the release commit `c6eaa706866b9868cb51048d64b3d21752abce44`, published as mhfe-core 0.1.0, on 2026-10-27. The first version of this record had it `fixed`, on the uncommitted tree; the earlier draft of this update had it `verified` at `4296f06`, a release commit replaced before publication.
- **Release blocking:** false. Low: availability of the user's own offline process on an input the host passes, with correct results and no disclosure.
- **Reported by:** security reviewer (CHECK-SEC-007); reported independently by the protocol reviewer as a FUN finding (CHECK-API-004) and by the api reviewer as an API finding (CHECK-API-001). One root cause, so one ID.
- **Checks:** CHECK-SEC-007, CHECK-API-004, CHECK-API-001.
- **Affected files and builds:** `src/nfkd.rs:41-67` (Nfkd::write; from_utf8 at :53-55, rotation at :59); `src/nfkd.rs:72-77` (insertion_point); `src/wallet_check.rs:53-55` (Seed::derive); `src/wallet_check.rs:116` (draw).
- **Reproduction:** Build the security harness and run `input-bounds`, or call `Seed::derive(&phrase, &format!("a{}", "\u{301}".repeat(65536)))`: one letter followed by 128 KiB of U+0301 COMBINING ACUTE ACCENT. `wallet_check::draw(passphrase, fill)` normalizes the passphrase the same way before its first fill. The protocol harness's `nfkd_cost.py`, the api probe `nfkd` and three challenge harnesses (`skeptic-sec-nfkd`, `skeptic-fun-nfkd`, `skeptic-api-nfkd`) measure the same.
- **Expected behavior:** Normalizing a passphrase costs time linear in its length, or n log n like unicode-normalization's own `nfkd()` iterator, which sorts each run of non-starters once. The specification puts no length limit on the passphrase `Q` (its README.md:754 at `6f7537e`: the password's byte-length restrictions do not apply to `Q`), so the core may not refuse a long one.
- **Observed behavior:** `Nfkd::write` runs `std::str::from_utf8` over the whole pending run of non-starters for every non-starter it adds (src/nfkd.rs:53-55); for a mark out of order, `insertion_point` also scans back and line 59 rotates the bytes after the insertion point. The cost is quadratic in the length of one run. Measured by the security reviewer, release build, median of three: 0.057, 0.221, 0.870 and 3.454 s at 16, 32, 64 and 128 KiB (3.97 per doubling), against 0.003 to 0.004 s for ASCII of the same lengths, so PBKDF2 is not the cause. Out of order (U+0301 U+0316 repeated) it took 5.36 s at 128 KiB, and alternating marks 55.7 s at 320 KB. Runs of 30 marks, the limit of Unicode's stream-safe format, stay linear. The seeds are correct. The code it was cut from, mhfe `67e0b4c` (src/wallet.rs:1074-1080), used the `nfkd()` iterator.
- **Impact:** Availability only: no secret is exposed and no result is wrong. A passphrase read from a file, pasted, or passed by another program, with one run of tens of thousands of combining marks, holds the call for seconds; by extrapolation about 4 minutes at 1 MiB. Neither function can be cancelled while it normalizes; ending the process, which the specification allows, stops it. A typed line is not affected in practice: 4,096 marks in one run take 10 to 16 ms, and mhfe limits a typed line to 8 KiB. ### Assessment and limitations

The recorded evidence shows that, at `dec9c81`, the crate's protocol output agrees with specification 0.7.0 on every vector and every differential case run, that its Unicode 18.0.0 NFKD agrees with an oracle on every scalar value, that its secrets are owned and wiped on the paths read, and that on Linux its isolation holds as read back from the kernel. It also shows one Medium release-blocking defect in how the release would be published, and eight Low defects in availability bounds, an engine contract, documentation and CI. At the published release commit `c6eaa706866b9868cb51048d64b3d21752abce44`, seven of them are verified by CI run 40562937779, the full-cost replay 40563592519 and the reruns of the harnesses, AUD-002-SEC001 for every order of combining marks. The owner accepted the other two: the release keeps version 0.1.0, which a cache that fetched the withdrawn package still resolves to the withdrawn code (AUD-002-BLD001), and its notes do not list how it differs from that package (AUD-002-DOC001). No release blocker found by this audit remains in this crate. mhfe-core 0.1.0 was published from that commit: the package on crates.io, the GitHub release's signed `SHA256SUMS`, its asset and its build-provenance attestation all name the package this audit reproduced locally. The specification's record of the release is a separate step.

Limitations:

- This record is an evidence report with bounded execution. It is not a security certification, a cryptographic proof or proof that no other defect exists.
- No full-size Argon2id and no `--ignored` test ran locally, by instruction.
