# AUD-006 — Full audit of mhfe-core after the move onto reed-solomon-core

## Release decision

**INCOMPLETE**, ordinary audit. Every required row of the target matrix passed at the reviewed
commit, and no finding blocks a release. One required check is missing: Miri on the portable and
unsafe paths of the host could not run, because every path of the crate calls
secret-protection-core, whose first system call (`sigfillset`) Miri does not support, and the one
unsafe block needs that crate's work area. Obtaining it needs a Miri shim or a test build of
secret-protection-core that Miri can run. Android and iOS stay built and linted only
(AUD-006-ARC004, deferred).

### Findings

#### AUD-006-SEC001 — Low — In WebAssembly the repair profile leaves a container's word numbers in linear memory

- **Category:** SEC.
- **Severity:** low.
- **Status:** verified.
- **Release blocking:** false; a Low finding is fixed with the next change that touches its code.
- **Affected files and builds:** `src/repair.rs:62`, `src/repair.rs:128-144`,
  `src/repair/code.rs:1-8`, `src/repair/code.rs:52-58`.
- **Reproduction:** Build for wasm32 and call `Card::new` or `Repaired::of`: the stack arrays
  `data`, `received`, `unreadable`, `corrected`, `sources` and `outputs` keep the container's and
  the card's word numbers after the call, because `stack::cleared` (secret-protection-core's
  `with_cleared_stack`) clears nothing in WebAssembly.
- **Expected behavior:** The module documentation says the values are cleared; elsewhere the crate
  wipes such stack values itself (`phrase::word_of`) or keeps them in a `Secret` (`password_check`).
- **Observed behavior:** The arrays are never wiped, and `src/repair/code.rs` claims clearing
  without the native-only exception that `lib.rs` states.
- **Impact:** A WebAssembly host's linear memory keeps the word numbers of a container and its card
  until they are overwritten; native builds are not affected.
- **Evidence:** Source reading at the reviewed commit.
- **Recommended fix:** Hold the arrays in `zeroize::Zeroizing`, wiped on every path out, and say in
  the module documentation that stack clearing is native only.
- **Required verification:** The repair unit tests, the published repair vectors and the repair fuzz
  target pass.

#### AUD-006-API001 — Low — Seed::derive sends any passphrase's NFKD size to an allocation that ends the program

- **Category:** API.
- **Severity:** low.
- **Status:** verified.
- **Release blocking:** false; a Low finding is fixed with the next change that touches its code.
- **Affected files and builds:** `src/wallet_check.rs:49-55`, `src/nfkd.rs:29`, `src/nfkd.rs:42`.
- **Reproduction:** On wasm32, `Seed::derive(&phrase, &"\u{FDFA}".repeat(70_000_000))`: the NFKD
  counts 2.31e9 bytes, above `isize::MAX`, and `Secret::zeroed` ends the instance.
- **Expected behavior:** RUST-17: a size is checked before it reaches an allocation, or the contract
  says what happens. `Password::new` refuses its limit with `PasswordTooLong`.
- **Observed behavior:** Nothing bounds or documents the passphrase's size beyond asking a host to
  bound text it reads from a file or the clipboard.
- **Impact:** A host that passes an unbounded passphrase in WebAssembly ends its program; no memory
  safety or secret is at stake. The specification sets no passphrase limit.
- **Evidence:** Source reading at the reviewed commit.
- **Recommended fix:** State in `Seed::derive`'s documentation that a passphrase whose NFKD the
  memory cannot hold, never more than 2 GiB in WebAssembly, ends the program.
- **Required verification:** Documentation review; the new passphrase fuzz target compares the seed
  with bip39's.

#### AUD-006-BLD001 — Low — fuzz/Cargo.lock resolves other versions than Cargo.lock and no RustSec check reads it

- **Category:** BLD.
- **Severity:** low.
- **Status:** verified.
- **Release blocking:** false; a Low finding is fixed with the next change that touches its code.
- **Affected files and builds:** `fuzz/Cargo.lock`, `.github/workflows/audit.yml:7-17`.
- **Reproduction:** Compare the two lockfiles: sha2 0.11.2, ctutils 0.4.8 and syn 3.0.10 in
  fuzz/Cargo.lock against 0.11.1, 0.4.6 and 3.0.9 in Cargo.lock; audit.yml reads Cargo.lock only.
- **Expected behavior:** The fuzz runs exercise the dependency graph the tests, the notices and
  RustSec see.
- **Observed behavior:** Three shared packages differ, and libfuzzer-sys, cc and the other fuzz-only
  crates get no advisory check in CI.
- **Impact:** A release's 90-second fuzz runs test a slightly different graph; an advisory against a
  fuzz-only crate would go unnoticed in CI.
- **Evidence:** Source reading at the reviewed commit.
- **Recommended fix:** Pin the three packages to the root versions, and add a RustSec step and paths
  entry for fuzz/Cargo.lock.
- **Required verification:** No package shared by the two lockfiles differs; `cargo deny` and `cargo
  audit` pass for both; audit.yml lists fuzz/Cargo.lock.

#### AUD-006-ARC001 — Low — The Linux isolation test expects NoMemoryReading from the PID namespace alone

- **Category:** ARC.
- **Severity:** low.
- **Status:** verified.
- **Release blocking:** false; a Low finding is fixed with the next change that touches its code.
- **Affected files and builds:** `tests/isolation.rs:500-510`, `tests/isolation.rs:208-215`.
- **Reproduction:** Run the isolation test in a user namespace its user owns without a new PID
  namespace (`unshare --user --map-current-user`): secret-protection-core 0.2.0 reports `Unknown`,
  and the test expects `Confirmed`.
- **Expected behavior:** Since secret-protection-core 0.2.0, NoMemoryReading is confirmed only for a
  program started in the first user namespace as well as the first PID namespace.
- **Observed behavior:** The test checks the PID namespace only, and asserts that the parent cannot
  open the child's memory, which it can in such a user namespace.
- **Impact:** The test fails where the library is right; CI's runners start in the first user
  namespace, so no run failed.
- **Evidence:** Source reading at the reviewed commit.
- **Recommended fix:** Read the user namespace before the isolation and require both, as
  secret-protection-core's own test does; check the parent's refusal only in the first user
  namespace.
- **Required verification:** The isolation program passes on Linux; its expectations match
  secret-protection-core 0.2.0.

#### AUD-006-ARC002 — Low — The code-rules gate reads fuzz builds and corpora and counts no fuzz target's lines

- **Severity:** low.
- **Status:** verified.

- **Reproduction:** After any fuzz build, `cargo xtask code-rules` reads fuzz/target (generated Rust

- **Recommended fix:** Skip fuzz/target, fuzz/corpus, fuzz/artifacts and fuzz/coverage, count

#### AUD-006-ARC003 — Low — Recovery readings and the wallet check's passphrase have no fuzz target

- **Category:** ARC.
- **Severity:** low.
- **Status:** verified.
- **Release blocking:** false; a Low finding is fixed with the next change that touches its code.
- **Affected files and builds:** `fuzz/Cargo.toml`, `src/recovery.rs:59`, `src/wallet_check.rs:54`.
- **Reproduction:** List the fuzz targets: phrase, password, repair, password_check. None reaches
  `Recovery::readings` with any stated length, or `Seed::derive` with a passphrase that
  `Password::new` would refuse (control characters, unassigned code points, over 1,024 bytes).
- **Expected behavior:** RUST-18: every parser and reader of untrusted input has a fuzz target.
- **Observed behavior:** Two inputs a person gives, a stated length and a passphrase, reach no fuzz
  target.
- **Impact:** Inputs outside the unit tests' cases are not explored on these two paths.
- **Evidence:** Source reading at the reviewed commit.
- **Recommended fix:** Add a recovery target (a stand-in engine, any container, any stated length:
  each reading reads back, and is verified exactly when its length's verifier matched) and a
  passphrase target (the seed equals bip39's of the passphrase's NFKD). The phrase target also
  writes valid phrases as a person may, so that it reaches the checksum.
- **Required verification:** Each new target runs without a crash; the release workflow lists them
  through `cargo fuzz list`.

#### AUD-006-ARC004 — Low — Android and iOS run on no runner though an emulator and the simulator exist

### Informational observations and recommendations

- On macOS the isolation test checks the report alone: no process tries to read the child. mhfe's
  `cargo xtask hardened` shows a positive and a negative control with `task_for_pid` as root; the
  same here would make the hardened run prove the refusal.
- H0 and the final block hash of argon2 are removed by stack clearing alone, as its `zeroize`
  feature is off; defence in depth only.
- `Recovery::detected_lengths` keeps the original's possible word counts in an ordinary heap vector;
  negligible.

### Assessment and limitations

The evidence shows the crate's own code and its integration with reed-solomon-core and
secret-protection-core behave as specified on every native runner GitHub offers and in WASI, with
the published vectors, four fuzz targets for five minutes each and no advisory against either
lockfile. It does not show the absence of other defects, Miri's view of the unsafe block, the
Android and iOS runs, or the full-cost vectors, which vectors.yml runs on a tag. The construction
itself has not been reviewed by independent cryptographers.
