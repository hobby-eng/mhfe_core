### Findings

#### AUD-003-SEC001 — Low — Under lto = "thin", bytes 40 to 55 of H0 stay on a pool thread's stack after argon2id returns, above the frame the overwrite starts from

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** At 0daa611 (the tree of be64462 is identical): src/engine/native.rs:93-94 (the hash runs directly in the job frame) and :119-122 (the only clearing); src/stack.rs:29-37 (`overwrite` clears only below its own frame). Claims it breaks: src/engine/native.rs:1-2, :29-30, :72-74, :119-121, :249-252 and SECURITY.md:31-36. Builds: measured on Linux x86-64 with rustc 1.99.1. Residue with the host profile lto = "thin" at opt-level 3 (at 40 to 55 bytes above the sleeping stack pointer) and at opt-level 2 (at 104 to 119 bytes above it), default codegen units. No residue found at: default release, mhfe's profile (fat LTO, one codegen unit, panic=abort, opt-level 3), lto=true alone, panic=abort alone, codegen-units 1 and 4, opt-level 0, 1, 2, s and z without LTO, thin LTO with codegen-units=1, with panic=abort or with opt-level s, fat LTO with target-cpu=native, and overflow checks on. A crate is built with each host's profile, so this cannot be settled by the crate's own profile. The real mhfe binary was not built (the brief forbids it).
- **Reproduction:** Carried out. From the repository root, with CARGO_TARGET_DIR set to a build folder: `docs/audits/AUD-003-harnesses/sec/run-matrix.sh thin CARGO_PROFILE_RELEASE_LTO=thin`. The probe depends on the real crate, calls the public NativeArgon2::new and argon2id at 1 MiB, one pass, a 20-byte password, waits until the four threads sleep, reads their stacks through /proc/self/mem from the main thread, and searches every byte offset for every 8-byte window of the password, H0 and the tag and for the block words. It prints 38 hits when nothing is left (its own heap copies of the password and tag) and exits 0. Add CARGO_PROFILE_RELEASE_OPT_LEVEL=2 for the second position. `probe-stack hold 400 1024 1 20` under docs/audits/AUD-003-harnesses/sec/gdb-hold.txt stops with the words on the stack.
- **Expected:** native.rs:1-2: the engine has four threads of its own, "which it leaves clean after every call". native.rs:119-121: RustCrypto leaves H0, the hashes and the blocks on the stacks, and since a pool thread lives on, nothing else ever clears them, so the overwrite does. SECURITY.md:31-36 says the same. CORE-24: a secret is wiped when its work ends. H0 is secret: it is a hash of the password and the salt, and everything after it follows from it.
- **Observed:** Exit 1 with `thin scan 40 calls: 110 hits`: in 8 of 20 scans, nine 8-byte windows of H0 (offsets 40 to 48, so bytes 40 to 55) stand at 40 to 55 bytes above the sleeping stack pointer of one pool thread; opt-level 2 gives the same bytes in 7 of 20 scans. No password, tag or block word was found. gdb shows the frames at that moment as syscall, Sleep::sleep, wait_until_cold, ThreadBuilder::run, so the bytes lie in slots of Sleep::sleep's live frame that nothing writes. The real engine changes the stack down to about 128 KiB below the sleeping stack pointer, so `overwrite`'s array starts close to that pointer, and the words lie above it. Cause: the compute job and the broadcast job start at the same depth, in wait_until_cold. Frames of the broadcast, of `overwrite` and of the idle loop cover the top of the compute's frames without writing every byte, and `overwrite` clears only below itself. Default release is clean only because H0 lands deeper there. The stack test passes in the same profile (unit-stack-test-thin), since it reads only below its own frame and searches only block words, so the comment at native.rs:249-250 that these words stand for all that RustCrypto leaves does not hold.
- **Impact:** Sixteen bytes of H0 of the last call stay in ordinary unlocked stack memory while the thread sleeps, which can be for the rest of the engine's life, for instance while mhfe shows a phrase. That memory can reach swap, a hibernation image or a core dump of a host that did not isolate itself, and root can read it directly, unlike a Secret in secret memory. Prerequisites: a host built with thin LTO, and someone reading that memory. Limits: no direct secret compromise is shown. The last call of encrypt, decrypt or rekey is round 0, whose salt comes from a half of the secret state, so these bytes alone give no cheap password test. A snapshot taken right after a forward round 11, whose half stands in the container, would give a test at BLAKE2b speed without any Argon2 work. In the one `hold` run the words were gone at those addresses after the engine was dropped. mhfe's own profile showed none in the probe.
- **Fix:** Keep the reviewer's change in compute: `self.threads.install(|| stack::cleared(|| argon2.hash_password_into_with_memory(password, salt, key, blocks))).map_err(refused)`. The broadcast stays for the other three threads.

Change the stack test in the same commit, because the thread of the hash now clears itself. Run it at 8192 KiB instead of 1024, require `>= LANES as usize - 2`, and keep `assert!(worked)`. In the first release-mode test run, the copy passes 0 of 400 failed across 1 to 16 CPUs, and the no-broadcast mutant still fails. Debug runs of the 8 MiB test take about 1.5 s; the 8 MiB plus LANES-2 combination was run in release only. The tried diff is docs/audits/AUD-003-harnesses/skeptic-sec/sec001-fix-with-stack-test.diff.

Adjust the comments at native.rs:72-74, :119-121, :249-250 and :261-262, and stack.rs:13-16. No test for the H0 bytes is proposed: a default build shows none, so such a test could not fail; the fix holds by construction.

#### AUD-003-API001 — Low — A low RUST_MIN_STACK ends the process on a pool thread of NativeArgon2, which sets no stack size of its own

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** src/engine/native.rs:58-60 (ThreadPoolBuilder without stack_size) and :121 (broadcast of stack::overwrite); src/stack.rs:11 and :33 (the array of 128 KiB). The texts that leave the engine out of the stack need: src/lib.rs:24-27, README.md:65-69, SECURITY.md:27-30. Every native target, at 0daa611. 0.1.0 is not affected.
- **Reproduction:** Carried out. From the repository root, with <target> a Cargo target folder outside it: CARGO_TARGET_DIR=<target> cargo build --release --locked --offline --manifest-path docs/audits/AUD-003-harnesses/fun/Cargo.toml; then RUST_MIN_STACK=131072 <target>/release/aud003-fun-engines call audited, and the same with `call published`.
- **Expected:** The same results as the program replaced (RUST-14): 0.1.0 prints the tag under this variable. src/lib.rs:24-27 leaves the engine's calls out of the 140 KiB a call needs, and NativeArgon2::new's doc (src/engine/native.rs:37-39) names what a thread can do: one the system refuses is Error::Argon2Failed. The comment at src/engine/native.rs:56-57 says an explicit number keeps RAYON_NUM_THREADS from steering the pool. RUST_MIN_STACK has the same reach over the pool's stacks and is not handled.
- **Observed:** At RUST_MIN_STACK=65536 and 131072 the audited engine prints "thread '<unknown>' has overflowed its stack" and "fatal runtime error: stack overflow, aborting", exit 134, at the first call. The published 0.1.0 prints its tag, exit 0, at the same values. At 147456 both print the tag e0e8eba3..., which fits the documented 140 KiB, here needed on a thread the host does not make.
- **Impact:** A person or launcher that sets the variable low gets an abort instead of a result or an Error. In mhfe it would hit the Argon2 check at start, before a secret is read. No wrong tag comes out, and an isolated process writes no core dump. In a process without isolation the abort comes in the overwrite, with the area not yet wiped, so a core dump, if the system keeps one, could hold it. Needs an unusual setting, hence low.
- **Fix:** In NativeArgon2::new give the pool its own stack: `.stack_size(THREAD_STACK_BYTES)` on the builder, with one named constant of 2 MiB, std's default, and extend the comment at native.rs:56-57 to say RUST_MIN_STACK has no say either. One call and one constant; no new check or error.

#### AUD-003-API002 — Low — NativeArgon2 and Mhfe<NativeArgon2> lost UnwindSafe and RefUnwindSafe, and the changelog does not say so

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** src/engine/native.rs:33 (the field `threads: ThreadPool`); CHANGELOG.md:3-33 (the 0.2.0 section). docs/public-api.txt lists items by name, so its gate cannot see this. Every native target, at 0daa611.
- **Reproduction:** Carried out. `<target>/release/aud003-fun-engines traits` from docs/audits/AUD-003-harnesses/fun prints the auto traits of both versions. A host of three lines also shows it: `let engine = NativeArgon2::new(64).unwrap(); let locked = std::panic::catch_unwind(|| engine.is_locked()); println!("{locked:?}");` built against 0.1.0 and against this commit (tmp probes probe-old and probe-new, bin catch).
- **Expected:** The 0.2.0 section is the record of what a host must know ("What changed:", CHANGELOG.md:5-7), and the commit behind it says every public item stays. cargo-semver-checks rates a lost auto trait as a major change (lint auto_trait_impl_removed: "A public type has stopped implementing one or more auto traits"; read in its repository). The change may ship in 0.2.0, but it should be recorded.
- **Observed:** 0.1.0: Send, Sync, Unpin, UnwindSafe and RefUnwindSafe are all true for both types. This commit: UnwindSafe=false and RefUnwindSafe=false for both, the other three true. The three-line host builds against 0.1.0 (exit 0) and fails against this commit (exit 101, error[E0277] on `dyn Fn(...)` types inside rayon-core, which the host's code does not name).
- **Impact:** Compile time only: host code that holds an engine or a Mhfe<NativeArgon2> across catch_unwind stops building at 0.2.0, with an error that points into rayon. No result changes. mhfe is not affected: its only catch_unwind is a test helper in src/word_wishes.rs:1020, away from the engine. Version 0.2.0 stays right, and this is one more reason a patch release could not carry the change.
- **Fix:** One sentence in the thread bullet of the 0.2.0 section (CHANGELOG.md:15-23): `NativeArgon2` and `Mhfe<NativeArgon2>` are no longer `UnwindSafe` or `RefUnwindSafe`, since rayon's `ThreadPool` is neither; a host that needs it wraps its closure in `AssertUnwindSafe`. No code changes.

#### AUD-003-BLD001 — Low — `cargo xtask vendored` passes with exit 0 when the one vendored file is missing and its folder remains, and its "is missing" branch can no longer be reached

- **Status:** fixed.
- **Release blocking:** false.
- **Affected:** xtask/src/vendored.rs:1-3 (the promise), 38-40 (a pass at a count of 0), 51-58 (recorded_digests), 95-97 (the unreachable branch), 181-193 (the unit test that reaches it only through a hand-built map), at 0daa611. It concerns the repository's tool only; the tool is not in the package.
- **Reproduction:** Carried out on an exported copy, never on the checkout: `git archive HEAD | tar -x -C <scratch>`, then in the scratch copy delete vendor/eff-large-wordlist/eff_large_wordlist.txt and leave its folder, then run `cargo xtask vendored`. The same script also tries a changed byte, an added file, a damaged SHA-256 row, a missing folder and the restored file.
- **Expected:** xtask/src/vendored.rs:1-3: "A file changed, added or missing fails." The brief: a check's ability to fail must stay. CHECK-ARC-002: a helper formerly needed must take part in the active path or be removed. CHECK-ARC-003: test-only seams must not give a false impression that production was exercised.
- **Observed:** With the file gone and the folder present the gate prints "The 0 vendored files are the recorded ones." and exits 0. recorded_digests returns a map only when the folder holds exactly one file, and that map holds that same path, so `recorded` can never name a path absent from `digests`. Since 4055e75 deleted the sha256sum list, which was the only source of such a path, the loop at lines 95-97 cannot run in production; only a_file_changed_added_or_missing_is_refused reaches it, with a hand-built map of two files. The other four cases behave: changed exit 1, added exit 1, damaged row exit 1, folder missing exit 1 by the read_dir error.
- **Impact:** Low. No wrong bytes can ship: build.rs stops on a missing list, so `cargo xtask check` still fails at its next build step, and a fresh clone has no folder at all, which fails at read_dir. The defect is that the gate and its test claim a refusal the gate does not make, and the multi-file shape (TREES, the recursion in digests_of, the maps) is left over from the deleted Argon2 tree.
- **Fix:** Name the file with its tree, and let the row give the record whatever the folder holds: `const TREES: &[(&str, &str)] = &[("eff-large-wordlist", "eff_large_wordlist.txt")];`, `for (tree, file) in TREES` in `run`, and `fn recorded_digests(document: &str, file: &str) -> BTreeMap<String, String> { document.split('\n').find_map(table_row).map(|digest| BTreeMap::from([(file.to_owned(), digest.to_owned())])).unwrap_or_default() }`. The `paths` logic goes, and `differences` reports changed, added and missing as written. Also reword the doc comment at lines 49-50, and in the_table_row_gives_the_digest_of_a_tree_of_one_file_only drop the two-file case and rename the test, since 'one file only' no longer describes it.

### Assessment and limitations

No medium or higher finding. The evidence shows the tested paths on this tree and is no certification.

- Not run: an older kernel, a processor without AVX2. macOS file writes are read back on CI only.
- sec: Nothing was run on AArch64, macOS, iOS, Windows or Android: stack scans and thread behaviour there rest on reading and on frame sizes from assembly. Whether the H0 residue appears on those targets in any profile is unknown. CI results were not read.
- sec: No kernel other than 7.0.0-42 was run: older kernels, 16 and 64 KiB pages rest on reading.
- sec: The real mhfe binary was not built against this version; mhfe's profile was reproduced in the probe only, and its fat LTO could inline differently there.
- sec: Only rustc 1.99.1 was tried. Stack layout, and so the residue, can change with any compiler, or with later blake2, rayon or crossbeam versions, which are carets for a host.
- sec: The plain, non-AVX2 compress path was not run: this machine has AVX2 and no switch forces the other path.
- sec: No scan at full cost (2 GiB): frames do not depend on memory or passes, as depth runs at 1 and 16 MiB showed. Registers were not read.
- sec: No Miri or ThreadSanitizer run: neither is available on this stable toolchain.
- sec: The search patterns cover the password, H0, tag, the XOR of the last blocks and block words. Other values, such as compress temporaries, were covered only by a listing of high-entropy words by stack offset in three profiles and in thin LTO.
- sec: rayon's `join`, `sleep` and crossbeam internals were read only where the broadcast and start paths need them. params.rs beyond line 330 and argon2's PHC code were not read, as the engine does not use them.
- fun: The full-cost corpus: not run here. CI runs it and the coordinator reads the result; here only one tag at 2 GiB and 12 passes ran on each engine, none at 3 GiB and no transcript.
- fun: Memory levels above 1 and high PIMs: checked by reading argon2 0.6.0 only (no overflow at 3 << 30 KiB or 12,288 passes), never run.
- fun: The plain, non-AVX2 path on x86-64: this machine runs AVX2; the same source runs plain on CI's ARM64 per the commit, which was not read here.
- fun: AArch64, macOS, Windows, iOS and Android: nothing ran there. Thread creation under Windows' isolation with rayon rests on the documents.
- fun: A host of several threads that makes its engine on another thread: read in native.rs and rayon's spawn path, not run.
- fun: A host's own blake2 version: Cargo.lock pins it here, while a program's build may move it within 0.11.
- fun: rayon, rayon-core and crossbeam internals beyond the builder and spawn lines; argon2 0.6.0's clearing and stacks are the security reviewer's.
- fun: Code unchanged since v0.1.0, which AUD-002 covers, beyond where the change touches it. README.md's statement about needing no C compiler is left to the build reviewer.
- bld: The CI jobs on Android, iOS, macOS, Windows, ARM64 Linux, WASI and MSRV were reviewed statically and not run here; their results are the coordinator's. In particular, the iOS link without IPHONEOS_DEPLOYMENT_TARGET has never been tried outside CI, so that job's result is the only proof.
- bld: The full-cost vectors were not run.
- bld: The upstream comparison covers argon2's src files only. The other new crates were checked by checksum, index, build scripts and manifests, not against their repositories, and the internals of rayon and crossbeam were not audited.
- bld: Yank state is live for the eight new crates. For the other crates it comes from the local index cache, of unknown age per crate.
- bld: cargo audit used the local advisory database of 2026-10-30 and did not fetch a newer one.
- bld: The private vulnerability-reporting setting was not rechecked; it is unchanged since AUD-002.
- bld: docs/public-api.txt was checked by its gate only, and the AUD-002 harnesses and report were not reread.
